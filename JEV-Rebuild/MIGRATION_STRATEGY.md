# JEV 自动成交持久化蓝图 - 最小集迁移策略

## 目标
- 不清库也能跑
- 平滑迁移到新的权威存储架构
- 确保数据一致性和完整性

## 一、迁移策略

### 1. 消息迁移（CHAT_ROOM_DO）
- **迁移时机**：首次访问客户聊天时
- **迁移流程**：
  1. 检查 CHAT_ROOM_DO 是否存在消息记录
  2. 若不存在，从旧存储（INBOX_KV）拉取历史消息
  3. 调用 `appendMessage` 方法逐个添加消息（利用幂等性去重）
  4. 迁移完成后，标记迁移状态

### 2. 联系人迁移（CONTACT_INDEX）
- **迁移时机**：首次获取客户列表时
- **迁移流程**：
  1. 检查 CONTACT_INDEX 是否为空
  2. 若为空，从旧存储（INBOX_KV）拉取客户信息
  3. 调用 `updateContact` 方法逐个更新联系人信息
  4. 迁移完成后，标记迁移状态

### 3. 媒体迁移（R2）
- **迁移时机**：首次访问包含媒体的消息时
- **迁移流程**：
  1. 检查 R2 中是否存在媒体文件
  2. 若不存在，从旧存储拉取媒体文件并上传到 R2
  3. 更新消息记录中的 `media_keys` 字段
  4. 迁移完成后，标记迁移状态

### 4. 翻译迁移（TRANSLATION_STORE）
- **迁移时机**：首次访问需要翻译的消息时
- **迁移流程**：
  1. 检查 TRANSLATION_STORE 是否存在翻译记录
  2. 若不存在，从旧存储拉取翻译记录
  3. 调用 `storeTranslation` 方法存储翻译结果
  4. 迁移完成后，标记迁移状态

### 5. 成交状态迁移（DEAL_STATE_DO）
- **迁移时机**：首次分析客户成交状态时
- **迁移流程**：
  1. 检查 DEAL_STATE_DO 是否存在成交状态
  2. 若不存在，初始化默认成交状态
  3. 调用 `ingestMessage` 方法分析历史消息
  4. 迁移完成后，标记迁移状态

## 二、去重与游标策略

### 1. 消息去重策略
- **去重键**：`message_id`
- **去重机制**：
  - CHAT_ROOM_DO 内部维护 `processedMessageIds` Set
  - `appendMessage` 方法先检查消息 ID 是否已存在
  - 若存在，返回 `duplicated: true`，不重复存储
  - 若不存在，存储消息并添加到去重集合

### 2. 游标策略
- **游标定义**：基于消息时间戳和偏移量的组合
- **实现方式**：
  - `fetchMessages` 方法支持 `since` 和 `cursor` 参数
  - `since`：时间戳，默认从 0 开始
  - `cursor`：偏移量，默认从 0 开始
  - 返回结果包含 `cursor` 和 `hasMore` 字段

### 3. 增量拉取策略
- **客户端**：
  - 首次拉取：`since=0, cursor=0`
  - 后续拉取：使用上次返回的 `cursor` 和 `last_message_ts`
- **服务端**：
  - 基于 `since` 过滤消息
  - 基于 `cursor` 和 `limit` 分页
  - 计算 `nextCursor` 和 `hasMore`

## 三、数据一致性保证

### 1. 写入顺序
- **媒体写入**：先写 R2 成功 → 再写 messageRecord.media_keys
- **消息写入**：先写 CHAT_ROOM_DO 成功 → 再更新 CONTACT_INDEX
- **翻译写入**：先写 TRANSLATION_STORE → 再更新 UI 状态

### 2. 错误处理
- **R2 写入失败**：禁止写 media_key，避免 404
- **DO 写入失败**：返回错误，禁止继续操作
- **KV 写入失败**：记录错误，尝试重试

### 3. 幂等性保证
- 所有写入操作均支持幂等性
- 重复调用不会导致数据重复或不一致
- 基于唯一标识符（如 message_id）进行去重

## 四、迁移状态管理

### 1. 迁移状态字段
```json
{
  "migration": {
    "messages": true,    // 消息迁移完成
    "contacts": true,    // 联系人迁移完成
    "media": true,       // 媒体迁移完成
    "translations": true, // 翻译迁移完成
    "deals": true,       // 成交状态迁移完成
    "last_updated": 1234567890 // 最后迁移时间
  }
}
```

### 2. 迁移检查流程
- 每次启动服务时检查迁移状态
- 若未完成，触发相应的迁移流程
- 迁移过程中，确保新旧存储数据一致性
- 迁移完成后，优先使用新存储

## 五、性能优化

### 1. 批量操作
- 批量拉取旧存储数据
- 批量写入新存储
- 减少网络请求次数

### 2. 缓存策略
- 客户端缓存：localStorage 作为 cache
- 服务端缓存：内存缓存热点数据
- 缓存失效策略：基于时间戳

### 3. 并发控制
- 避免并发迁移同一个客户的数据
- 使用锁机制确保迁移过程的原子性
- 迁移失败时，支持断点续传

## 六、回滚策略

### 1. 回滚条件
- 迁移过程中发生严重错误
- 新存储不可用
- 数据一致性被破坏

### 2. 回滚流程
- 检测到回滚条件时，切换到旧存储
- 记录回滚原因和时间
- 待问题修复后，重新启动迁移流程

### 3. 数据验证
- 迁移完成后，验证新旧存储数据一致性
- 若不一致，触发自动修复流程
- 修复失败时，触发人工干预

## 七、监控与告警

### 1. 监控指标
- 迁移进度
- 迁移成功率
- 数据一致性
- 性能指标

### 2. 告警机制
- 迁移失败告警
- 数据不一致告警
- 性能异常告警
- 存储容量告警

## 八、总结

本迁移策略确保了在不清库的情况下，能够平滑迁移到新的权威存储架构，同时保证了数据的一致性和完整性。通过合理的去重和游标策略，避免了数据重复和不一致的问题，为系统的稳定运行提供了保障。
